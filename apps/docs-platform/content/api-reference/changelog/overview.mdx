## Description

The Changelog module exposes VeriWorkly's published release notes as structured data rather than
prose. Each entry carries its version, release type, and five separate change buckets — `added`,
`improved`, `fixed`, `breaking`, and `security` — so a consumer can render or diff them without
parsing markdown.

Entries originate two ways: authored directly in the admin console, or imported from GitHub
Releases by a daily job (`CHANGELOG_RELEASE_SYNC_CRON`, 06:00 UTC by default), which also resolves the pull requests
referenced in a release body into the `prRefs` array.

<Callout type="info" title="Reads here, writes in the admin router">
  These are read-only endpoints. Creating, editing, and deleting changelog entries lives under
  `/api/v1/admin/changelog`, which is not part of this public reference.
</Callout>

## Authentication

| Method | Access Level   | Requirement                                                                      |
| :----- | :------------- | :------------------------------------------------------------------------------- |
| `GET`  | **No session** | An API key with the `changelog:read` scope, or a whitelisted first-party origin. |

`changelog:read` is offered in the Studio scope picker and accepted by the API-key create and rotate
endpoints. See [API key scopes](/docs/api-keys#scopes).

## Caching

List responses are cached in Redis for `CHANGELOG_CACHE_TTL_SECONDS` (default 30 days), keyed by
type and page window. A request with a search term or a tag filter, or one that starts past row
200, is read from the database and not cached. An admin write clears the cache, so a newly
published release appears immediately rather than at the end of the TTL.

## Pagination

`GET /changelog` uses offset pagination: page size defaults to 20 and the most is 50, addressable as
either `limit`/`offset` or `page`/`pageSize`. A `limit` or `pageSize` above 50 is rejected with
`400`, and so is a request that sends both `page` and `offset`.
