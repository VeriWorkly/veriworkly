---
title: Resume Schema
description: TypeScript reference for ResumeData, MasterProfileData, and the customization model.
---

Every resume in VeriWorkly follows a type-safe schema defined in
[`apps/studio/types/resume.ts`](https://github.com/VeriWorkly/veriworkly/blob/master/apps/studio/types/resume.ts).
The Master Profile is defined once in `@veriworkly/profile-core` (`packages/profile-core/src/schema/schema.ts`)
and re-exported from that file.
The same shapes flow through the local store, the sync engine, both rendering engines, and every
export format.

---

## `ResumeData`: a single resume document

```typescript
export interface ResumeData {
  id: string;
  templateId: string;
  title?: string;
  language?: string;

  basics: ResumeBasics;
  links: ResumeLinks;
  summary: string;
  experience: ResumeExperienceItem[];
  education: ResumeEducationItem[];
  projects: ResumeProjectItem[];
  skills: ResumeSkillGroup[];

  languages: ResumeLanguage[];
  interests: ResumeInterest[];
  awards: ResumeAward[];
  certificates: ResumeCertificate[];
  publications: ResumePublication[];
  volunteer: ResumeVolunteer[];
  references: ResumeReference[];
  achievements: ResumeAchievement[];

  customSections: ResumeCustomSection[];
  sections: ResumeSection[];
  customization: ResumeCustomization;

  sync: ResumeSyncState;
  updatedAt: string;
}
```

Every standard section is a top-level typed array, the same eight extended arrays the Master Profile
has, so the hand-off from profile to resume loses nothing. `customSections` holds only sections the
user invented. `language` is the BCP-47 tag for the exported HTML.

---

## `MasterProfileData`: the canonical career record

The Master Profile holds the same typed arrays as a resume. Its type is inferred from the zod schema
in `@veriworkly/profile-core`, which also carries a `schemaVersion`.

```typescript
export interface MasterProfileData {
  schemaVersion: number;
  templateId: string;

  basics: ResumeBasics;
  links: ResumeLinks;
  summary: string;
  experience: ResumeExperienceItem[];
  education: ResumeEducationItem[];
  projects: ResumeProjectItem[];
  skills: ResumeSkillGroup[];

  languages: ResumeLanguage[];
  interests: ResumeInterest[];
  awards: ResumeAward[];
  certificates: ResumeCertificate[];
  publications: ResumePublication[];
  volunteer: ResumeVolunteer[];
  references: ResumeReference[];
  achievements: ResumeAchievement[];

  customSections: ResumeCustomSection[];
  sections: ResumeSection[];
  customization: ResumeCustomization;
  updatedAt?: string;
}
```

Unlike `ResumeData`, `MasterProfileData` carries no `id` and no `sync` state; it is a single
per-user record, synced through its own dedicated endpoints.

## Section control

```typescript
export type ResumeSectionId =
  | "basics"
  | "links"
  | "summary"
  | "experience"
  | "education"
  | "projects"
  | "skills"
  | "certifications"
  | "awards"
  | "publications"
  | "languages"
  | "interests"
  | "volunteer"
  | "references"
  | "achievements"
  | "custom";

export interface ResumeSection {
  id: ResumeSectionId;
  label: string;
  visible: boolean;
  order: number;
  column?: "left" | "right"; // For two-column templates
}
```

`sections` is what drives visibility and ordering in both the editor and the exports. Hiding a
section keeps its data intact while removing it from the rendered document. This is how one Master
Profile produces several differently-scoped resumes.

## Section schemas

### Basics and links

```typescript
export interface ResumeBasics {
  fullName: string;
  role: string;
  headline: string;
  email: string;
  phone: string;
  location: string;

  // Whether each field renders as a clickable link in exports
  linkEmail: boolean;
  linkPhone: boolean;
  linkLocation: boolean;
}

export type ResumeLinkType =
  | "github"
  | "linkedin"
  | "dribbble"
  | "twitter"
  | "portfolio"
  | "behance"
  | "medium"
  | "youtube"
  | "custom";

export type ResumeLinkDisplayMode = "icon" | "url" | "icon-username";

export interface ResumeLinks {
  displayMode: ResumeLinkDisplayMode;
  items: ResumeLinkItem[];
}

export interface ResumeLinkItem {
  id: string;
  type: ResumeLinkType;
  label: string;
  url: string;
}
```

<Callout type="info" title="Phone numbers: any country, stored as E.164">
  `phone` is optional. Studio, the server, and the portfolio share one rule from
  `packages/profile-core/src/common/phone.ts`: a value starting with `+` must be a valid number for
  its country (checked with `libphonenumber-js`) and is stored in E.164 form, for example
  `+442079460958`. A value without `+` is accepted only as 7 to 15 bare digits, kept as typed. An
  empty string means "not provided".
</Callout>

### Custom and extended sections

```typescript
export type ResumeAdditionalSectionKind =
  | "certifications"
  | "awards"
  | "publications"
  | "languages"
  | "interests"
  | "volunteer"
  | "references"
  | "achievements"
  | "custom";

export interface ResumeCustomSection {
  id: string;
  kind: ResumeAdditionalSectionKind;
  title: string;
  items: ResumeAdditionalItem[];
  editableTitle?: boolean;
}

export interface ResumeAdditionalItem {
  id: string;
  name: string;
  issuer: string;
  date: string;
  link: string;
  referenceId: string;
  description: string;
  details: string[];
}
```

`ResumeAdditionalItem` is the generic item shape for sections the user invented. New writes use
`kind: "custom"`; a section stored with an older kind is folded back into the matching typed array
when the document is normalised.

The typed arrays (`ResumeLanguage`, `ResumeAward`, `ResumeCertificate`,
`ResumePublication`, `ResumeVolunteer`, `ResumeReference`, `ResumeAchievement`, `ResumeInterest`)
carry their own per-kind fields. For example, `ResumeLanguage.fluency` is a union of `"elementary" |
"limited" | "professional" | "fluent" | "native"`, and award/certificate/publication entries each
carry an optional `website` plus a `showLink` toggle.

## Customization

```typescript
export interface ResumeCustomization {
  fontFamily: string;
  theme?: string;

  accentColor: string;
  textColor: string;
  mutedTextColor: string;
  pageBackgroundColor: string;
  sectionBackgroundColor: string;
  borderColor: string;
  sectionHeadingColor: string;

  sectionSpacing: number;
  pagePadding: number;
  bodyLineHeight: number;
  headingLineHeight: number;
}
```

| Property                                         | Effect                                                                                |
| :----------------------------------------------- | :------------------------------------------------------------------------------------ |
| `fontFamily`                                     | Selects a family from the shared font registry, which also drives PDF font embedding. |
| `accentColor`                                    | Headings, rules, and link colour.                                                     |
| `textColor` / `mutedTextColor`                   | Primary and secondary body text.                                                      |
| `pageBackgroundColor` / `sectionBackgroundColor` | Page canvas and section block backgrounds.                                            |
| `borderColor`                                    | Dividers and section rules.                                                           |
| `sectionHeadingColor`                            | Section heading text, independent of `accentColor`.                                   |
| `sectionSpacing`                                 | Vertical gap between section blocks.                                                  |
| `pagePadding`                                    | Page margins.                                                                         |
| `bodyLineHeight` / `headingLineHeight`           | Typographic line heights.                                                             |

Both the web engine and the PDF engine read this same object, which is what keeps the on-screen
preview and the exported file visually aligned.
