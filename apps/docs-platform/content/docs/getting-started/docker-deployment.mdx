The repository ships a `compose.yaml` with four production services and one development-only
service.

| Service        | Image / build                                 | Port             | Role                                                                                                                      |
| :------------- | :-------------------------------------------- | :--------------- | :------------------------------------------------------------------------------------------------------------------------ |
| `web`          | Built from the root `Dockerfile`              | `127.0.0.1:3000` | The **marketing site** (`apps/site`), built with Next.js standalone output.                                               |
| `api`          | Built from `apps/server/Dockerfile`           | `127.0.0.1:8080` | The Express API.                                                                                                          |
| `migrate`      | The `build` stage of `apps/server/Dockerfile` | none             | Runs `prisma migrate deploy` once, then exits. `api` starts only after it succeeds.                                       |
| `redis`        | `redis:7-alpine`                              | internal         | Cache, sessions, rate limiting, quotas, and job locks. Password-protected, memory-capped, persisted to a volume with AOF. |
| `redisinsight` | `redis/redisinsight:2.70.1`                   | `127.0.0.1:5540` | A browser GUI for inspecting Redis. Starts only with `docker compose --profile dev up`.                                   |

<Callout type="warn" title="Keep `redisinsight` off servers">
  It has unauthenticated read and write access to Redis, which is where sessions live. It is in the
  `dev` profile, so a plain `docker compose up` never starts it, and it listens on loopback only.
  Reach it over an SSH tunnel if you need it.
</Callout>

<Callout type="warn" title="What Compose does and does not deploy">
  The `web` service builds **only the marketing site**. Studio, the portfolio builder, the
  documentation site, and the blog are **not** part of this Compose file. Deploy those separately if
  you need them.
</Callout>

<Callout type="warn" title="PostgreSQL is not containerised">
  Because production-grade persistence, backups, and volume management are deployment-specific,
  `compose.yaml` expects an **external** PostgreSQL instance (Neon, AWS RDS, a managed VPS, and so
  on). Provide its connection string via `DATABASE_URL`.
</Callout>

## Prerequisites

- **Docker Engine** 24 or higher.
- **Docker Compose** v2 or higher.
- An external **PostgreSQL** database and its connection string.

## Configuration

<Steps>
  <Step>
    ### Create the environment files

    ```bash
    # Values consumed by compose.yaml itself
    cp .env.docker.example .env.docker
    ```

    `compose.yaml` reads everything from the file passed via `--env-file`, so `.env.docker` is the
    single source of truth for a containerised deployment. Every variable the API refuses to boot
    without is marked required in `compose.yaml`, so `docker compose up` names the missing ones
    before any container starts: `DATABASE_URL`, `ALLOWED_ORIGINS`, `TRUST_PROXY`,
    `WEB_CONCURRENCY`, `REDIS_PASSWORD`, `AUTH_SECRET`, `AUTH_BASE_URL`, `ADMIN_EMAIL`,
    `API_KEY_HASH_SECRET`, `ANALYTICS_HASH_PEPPER`, `PORTFOLIO_URL`, `PORTFOLIO_REVALIDATE_SECRET`,
    the Dodo API key, webhook secret and three redirect URLs, and the five `R2_*` values.

    `REDIS_PASSWORD` goes into the Redis URL as is, so use letters and digits only (for example
    `openssl rand -hex 32`).

  </Step>

  <Step>
    ### Configure network resolution

    Three URL variables control how traffic is routed:

    - **`NEXT_PUBLIC_BACKEND_URL`**: the publicly reachable API endpoint used by the browser, for
      example `https://api.yourdomain.com/api/v1`. This is baked in at build time.
    - **`BACKEND_INTERNAL_URL`**: the address Next.js uses for server-side rendering inside the
      Docker network. It defaults to `http://api:8080/api/v1`.
    - **`ALLOWED_ORIGINS`**: a comma-separated list of frontend origins the API accepts CORS
      requests from. It must include your public site URL, and every entry must be `https://`.

  </Step>

  <Step>
    ### Set production-required variables

    The API runs a fail-fast configuration validator at boot when `NODE_ENV=production`. It refuses
    to start unless these hold:

    - `AUTH_SECRET` is at least 32 characters and not an example value.
    - `AUTH_BASE_URL` and the other public URLs use HTTPS and do not point at localhost.
    - `TRUST_PROXY` is a hop count or an IP/CIDR list. `true` and `false` are **rejected**: `true`
      lets a client spoof `X-Forwarded-For`, and `false` puts every visitor behind the proxy's one
      IP. Behind a single nginx, set `TRUST_PROXY=1`; with Cloudflare in front of nginx, see the
      notes in `apps/server/.env.example`.
    - `API_KEY_HASH_SECRET` is set and is **different** from `AUTH_SECRET`.
    - `AUTH_EMAIL_PROVIDER` is `resend` (with `RESEND_API_KEY`) or `smtp` (with host, user and
      password). Compose defaults it to `resend`. The `console` provider only logs codes and is
      refused.
    - `AI_API_KEY` is set and the AI policy defines both modes for every action.
    - Dodo Payments and all five Cloudflare R2 credentials are present.

    The [Environment Variables](/docs/operations/environment-variables#production-requirements)
    page lists every rule.

    This is deliberate: a misconfigured production deployment fails at boot rather than silently
    breaking on the first real checkout or upload.

  </Step>
</Steps>

## Deployment

<Steps>
  <Step>
    ### Build and start

    From the repository root:

    ```bash
    docker compose --env-file .env.docker up -d --build
    ```

    Compose starts `redis` and runs `migrate`. `api` starts once Redis is healthy and the
    migrations have applied, and `web` starts once the API reports healthy.

  </Step>

  <Step>
    ### Verify

    ```bash
    # Service status
    docker compose ps

    # Unified logs
    docker compose logs -f

    # API logs only
    docker compose logs -f api
    ```

    Then confirm the API's dependency connections:

    ```bash
    curl http://localhost:8080/api/v1/health/ready
    ```

    `/health/ready` probes PostgreSQL and Redis. `/health` is a lightweight liveness check that does
    not touch either. The container health check uses `/health` deliberately, so an uptime probe
    does not keep serverless database compute awake.

  </Step>
</Steps>

## Production hardening

Compose binds `web` and `api` to `127.0.0.1` only, so a **reverse proxy / TLS terminator** on the
host (Nginx, Traefik, or Caddy) is the only way in. It handles:

- **TLS termination**: the API's configuration validator requires an HTTPS `AUTH_BASE_URL`.
- **Domain routing**: mapping `yourdomain.com` to `127.0.0.1:3000` and `api.yourdomain.com` to
  `127.0.0.1:8080`.
- **Client addresses**: forward the visitor's IP in `X-Forwarded-For` and set `TRUST_PROXY` to the
  number of proxies in front of the API.

If you also deploy the portfolio builder, free portfolios are served under a path on its own host,
and premium portfolios on wildcard subdomains (`*.yourdomain.com`), which need a wildcard DNS record
and a wildcard TLS certificate.

## Updating

```bash
# Pull the latest source
git pull origin master

# Rebuild and restart
docker compose --env-file .env.docker up -d --build
```

The `migrate` service applies new migrations on every `up`, before the new API starts, so the
running code never sees an older schema than it expects. Migrations need a direct database
connection: if `DATABASE_URL` goes through a pooler, set `DIRECT_DATABASE_URL` to the non-pooled
endpoint.

The API drains in-flight requests and running jobs on shutdown, so Compose gives it 40 seconds
(`stop_grace_period`) before killing it.
